# 10 · 世界书（WorldBook / World Info）编写合并参考

> 三源合并：`worldbook-skill`（条目落地与配置）、`ln-lore-pipeline`（二创长作证据链与世界书工程）、`chunshui-fengyue`（通用质检与触发审计）。只写**可执行判据**；来源冲突标 `A 派 / B 派 / C 派`，不强行统一。术语保留英文：`character_book`、`keys`、`secondary_keys`、`position`、`depth`、`insertion_order`、`constant`、`selective`、`scan_depth`、`prevent_recursion`、`exclude_recursion`、`disable`。

## 0. 三源定位（先决定用哪派）

| 源 | 定位 | 独有强项 |
|---|---|---|
| **A 派** worldbook-skill | 条目落地执行层 | 蓝绿灯/order/双递归、XML 包裹 YAML、CLI 断言、`query.py` 自查 |
| **B 派** ln-lore-pipeline | 二创长作品流水线 | L 号直证、`uid` 十段、泄底 `disable`、十维四对照审查 |
| **C 派** chunshui-fengyue | 通用结构/触发/审稿 | 触发成本五层、场景用例审计、OR 语义陷阱、无姓名入口 |

A 派内部两阶段不可混：**世界观概念设计**（world-building-guide，只出文档不碰 YAML/配置）→ **条目化**（world-book-guide，只做转化与配置）。顺序颠倒＝返工。

## 1. 铁律速查（跨源一致）

| # | 规则 |
|---|---|
| 1 | **默认**所有条目 `prevent_recursion=true` **且** `exclude_recursion=true`，蓝灯绿灯都要（B 派：root + `extensions` 双层都写）——脚本默认 false，不写 flag 就没有；漏开→链式触发 token 爆炸、双向递归互相驱逐。**但这不是无条件铁律**，见下方 1.1 的三种例外 |
| 2 | 先判卡型再配置（1 核心角色=单卡，2+=多卡）；同一角色的拆分条目不等于多个角色 |
| 3 | 总纲第一个写并确认，再展开其他条目；每条写完立即 `query.py --brief` 复检；设定定稿后才写角色卡/开场白 |
| 4 | 关键词只用英文逗号 `,`；中文逗号/空格/分号＝整串被当成一个关键词 |
| 5 | trigger 是 **OR** 不是 AND；`[林知夏, 经历]` 任一词即命中 |
| 6 | 同名撞车必须全名+职名区分，并写"防串线句"（违者 P0） |
| 7 | 未核实不写；不确定项标 `[待核]` / `// 原文未提及` / "未载，不得臆造" |
| 8 | 不主动上 MVU/EJS/HTML；EJS 依赖 MVU，须先确认 MVU 已启用 |

### 1.1 双递归的三种例外（实测修正 · [Personal experiment] 2026-11-07）

`prevent_recursion` / `exclude_recursion` 的语义是「本条被触发时，是否受/是否产生链式影响」，**不是对错开关**。以下三种情况可以关，但必须能说出理由：

| 例外 | 判别 | 为什么能关 |
|---|---|---|
| 全常驻卡 | 所有条目 `constant=true` | 注入与否不靠触发决定，递归 flag 近乎无效 |
| 链式召回卡 | 需要「条目 A 被提及 → 顺带拉起条目 B」的设计（事件链、人物关系网） | 这正是递归要干的事；关掉反而丢效果 |
| 纯格式/UI 条目 | 作用是给模型输出格式，不承载事实 | 不参与设定推理，无链式风险 |

实测分布（用户提供的 5 张成熟卡，`st-card-study/` 可复核）：

| 卡 | 条目数 | prevent_recursion |
|---|---|---|
| 山海经 | 64 | 63 true / 1 false |
| 无职 1.0.1 | 91 | 82 true / 9 false |
| 青云宗 | 50 | 26 true / 24 false |
| 淫鬼驱魔录 | 15 | **15 false** |
| 女儿是本子画师 | 18 | **17 false** |

判断口径：**开了不心疼就开**；若你的卡需要条目互相拉起，关掉并写注释说明依赖关系，而不是默默留 false。

## 2. 分条粒度：按什么切

### 2.1 三条硬测试

| 测试 | 问法 | 通过 = 可独立成条 |
|---|---|---|
| 触发面 | 这条只在什么词/场景出现时才该被读到？ | 能说出 3~8 个具体触发词（含别名变体） |
| 自足 | 单独加载这一条，AI 会不会失去人格/看不懂？ | 不会（否则并入上位条目） |
| 复制 | 正文和其他条目重复吗？ | 零重复 |

### 2.2 五层职责分层（C 派）

| 层 | 内容 | 常驻 |
|---|---|---|
| 短核心 | 世界类型、制度不变量、互斥开局处理 | 少量常驻（勿塞长篇规范/全员履历/每轮状态规则） |
| 场景入口 | 列出该处少数 NPC：身份、当下动作、交互线索 | 场景触发 |
| 人物核心 | 全名/独有别名触发：识别点、动机、底线、关系、当下行为 | 人名触发 |
| 专题详档 | 经历、外貌、能力、复杂关系 | 自然短语查询 |
| 条件事件 | 前提、参与者目的、可观察起因、分歧、代价、重入条件 | 场景词 + 前提双判 |

### 2.3 A 派固定条目序列（order 即切分顺序）

| 阶段 | order | 定名 | 切分原则 |
|---|---|---|---|
| 1 | 1 | 世界观总纲 | 一条，不再拆 |
| 2 | 4 | 角色速览（多卡必写/单卡可跳） | 每角色 ≤2 行：姓名、身份、一句话特征 |
| 3 | 10~35 | 人物设定条目 | 每角色一条，XML 结构 |
| 4 | 35~45 | 性格条目 | **必须从人设独立成条**：基本信息是"她是谁"，性格是"她怎么行为"；混写会让 AI 读基本信息时错误调用性格标签 |
| 5 | 50~98 | 物品/能力/场景/事件 | 一类一条，关键词触发 |
| 6 | 99 / 100 | 角色详情补充 / NPC·故事 | 多卡绿灯；关键词触发 |

单卡内部编号：基础 10 → 外貌 20 → 性格 30 → 背景 40 → NSFW 50。

### 2.4 B 派 `uid` 十段结构（角色专属世界书）

| uid | 段 | 要点 | 状态 |
|---|---|---|---|
| 0 | ①核心元数据（卡外） | 全名/异写/自称/身份/**防串线句** | `constant=false` |
| 1 | ②关系·羁绊 | 关系人名行，一行一证带 L 号 | 触发=关系人名 |
| 2 / 3 | ③前期锚点 / ③'终局锚点 | 低剧透事件 / 后期揭示 | 活跃 / `disable` 手动 |
| 4 | ⑤力量·战斗 | 能力词触发；**不编造咏唱** | 活跃 |
| 5 | ⑥语言指纹·防串线 | 句式 DNA / 称呼体系 / 引用守则 | 活跃 |
| 6 | ⑦台词库 | 「」逐字 + 话号，注明"说话者＝本人" | 活跃 |
| 7~9 | ⑦'⑨终局/红线 | 高阶剧透 | `disable` 手动 |

## 3. 每条多少 token / 多少字

| 对象 | 判据 | 出处 |
|---|---|---|
| 总纲（设计稿） | **100~200 字**，零度写作 | A / world-building-guide |
| 总纲（世界书条目） | **300~500 字**，自然段压缩 | A / world-book-guide |
| 角色速览 | 每角色 **≤2 行** | A |
| 条目预估 token（规划表） | 总纲 ~200；角色 ~350~400；物品 ~150；章节 ~200；禁词条目 ~120~150 | A |
| 人物详档 / 年表事件 | 无统一字数，自然紧凑；`title` ≤20 字、`description` 100~300 字含关键原句 | B / C |
| 命中正文预算 | 用**字符量**（空白计入），不是 token；"没有实际分词器不要称为 tokens" | C |
| 状态栏 900 字/6000 HTML | **只属状态栏**，不能偷换成整个世界书上限 | C |

> ⚠️ 100~200 vs 300~500 是 A 派内部两层：前者是设计阶段可逐行查询的数据库块，后者是写进世界书的条目正文。C 派反对一切题的硬性篇幅。

## 4. keys / secondary_keys 怎么写

| 条目类型 | keys 构成 | 示例 |
|---|---|---|
| 角色 | 全名,昵称,外号 | `秋明月,明月,秋姐` |
| NPC | 全名,昵称,外号,职务 | `王静,王老师,班主任` |
| 场景 | 场景名,所在区域,别称(+相关动作词) | `图书馆,主楼三层,自习室` |
| 物品 | 物品名,简称,相关词 | `秋水剑,秋水,佩剑` |
| 势力 | 全名,简称,所在地名 | — |

- 英文逗号分隔、无空格、无中文标点。错误：`林小雨，小雨，班长` / `林小雨 小雨 班长`。
- B 派硬要求：`key` 与 `keys` **镜像同步**；异写全部并写，"触发面设计勿清理"。
- `secondary_keys` = CLI `--keys2`（`keysecondary`）。**只有确认平台原生主/次关键词 AND 语义后**才能用双条件；未确认改用专名短语+入口提示，覆盖不足就说明限制。
- `selective` 默认 `false`；`selectiveLogic`：0=AND_ANY、1=NOT_ALL、2=NOT_ANY、3=AND_ALL。

| 坑 | 说明 | 做法 |
|---|---|---|
| OR 当 AND | 姓名挂满所有详档 → 每轮整套注入 | 详档用自然短语：`林知夏的旧事,林知夏的经历,林师傅以前的工作`；不要全局匹配"过去" |
| 宽泛词滥用 | 单人物小卡的"她"偶有合理用途，属**候选风险** | 逐案例决定，不机械全删也不默认加；职业通用词只引入该处合理人物 |
| 正则模拟组合 | 平台已报不支持 lookaround/backreference | 禁 `(?=…)`/`(?!…)`/反向引用；复杂正则须经目标引擎实测，"不要用 Python/JS 通过代替平台验证" |

扫描范围：默认限定最近 user/assistant，详细查询**优先 user**；**不要全局扫 system**（条目会互相触发）。

## 5. position / depth 怎么选

### 5.1 字段真值表（A 派，源自 SillyTavern `public/scripts/world-info.js:855-864`）

| position | 标识 | JS 常量 | 含义 | 用途 |
|---|---|---|---|---|
| 0 | ↑Char | `before_char` | 角色定义之前 | 宏观设定：总纲、规则、地理、历史 |
| 1 | ↓Char | `after_char` | 角色定义之后 | 具体信息：角色详情、NPC、场景、物品 |
| 2 | ↑AT | `ANTop` | Author's Note 之前 | 文风规则、格式指令、禁词条目 |
| 3 | ↓AT | `ANBottom` | Author's Note 之后 | 极少使用 |
| 4 | @D | `atDepth` | 指定深度 | 行为纠正、二次解释 |
| 5/6/7 | ↑EM/↓EM/Outlet | `EMTop`/`EMBottom`/`outlet` | 示例消息前后 / 指定 Outlet（需 `--outlet-name`） | A 派不用 |

`position=4` 必须配 `depth`；`role` 仅在 4 有意义（0=System / 1=User / 2=Assistant）。

### 5.2 冲突：depth 能用多大

| 派 | 说法 | 理由 | 适用 |
|---|---|---|---|
| **A 派** | **只用 `depth=0`；D1 及以上永不放任何条目** | 预设把聊天记录框起来告诉 AI"这是互动历史"，中间插设定破坏完整性；D0 在聊天记录最底部、影响力最强 | 常规 roleplay 卡；条目是**设定资料**而非当轮指令 |
| **B 派** | **强制 `position=4, depth=4`**（全条目统一），root + `extensions` 双层 | 配合"格式军规九条 + 全绿断言脚本"机械检查；紧贴聊天流做**防串线护栏/语言指纹/台词库** | 二创长作角色专属世界书；条目多是"AI 这轮该怎么表现" |

判据：条目是"世界是什么" → A 派（0/1）；是"AI 这轮该怎么表现" → D 位置。采用 B 派统一 `depth=4` 须先在目标 ST 版本实测裁剪与递归并记 `[待核]`；不要在同一本书里混用两派。

### 5.3 位置速查

| 内容 | position | order | constant | 备注 |
|---|---|---|---|---|
| 世界观总纲 / 背景·区域速览 | 0 | 1 / 2~3 | true | 总纲最前，AI 最先读 |
| 角色速览（多卡） | 0 或 1 | 4 | true | 若走 B 派 `uid0` 则 false |
| 角色详情（单卡） | 1 | 10~50 | true | 拆几条都蓝灯 |
| 角色详情（多卡） | 1 | 99 | false + keys | 绿灯 |
| 物品/场景/事件/NPC | 1 | 50~100 | false + keys | `scan_depth=2` |
| 二次解释/行为纠正 | 4, depth=0, role=0 | 1,2,… | false | 写"到早上时写出他喝牛奶"，不写"他习惯喝牛奶" |
| 禁词条目 | 2 | 1/2/3 | true | 每本书必含 3 条：叙事/比喻/描写 |

## 6. 什么时候 `constant`（蓝灯/绿灯）

| 派 | 规则 | 适用条件 |
|---|---|---|
| **A 派** | 单卡 → 该角色**所有**拆分条目 `constant=true`（拆 5 条=5 蓝灯，无例外）；多卡 → 速览蓝灯 + 各角色详情/性格绿灯 + keys 覆盖所有称呼；世界观条目蓝灯；NPC/场景/事件全部绿灯 + `scan_depth=2` | 世界书＝"这一个角色的完整档案"，角色必须每轮在场 |
| **B 派** | **全绿断言：`constant:true` 计数必须为 0**，全部靠 `keys`（含 `uid0`）；后期内容另走 `disable` 手动条目 | 二创 pipeline：条目量大、剧透分层严、要机械断言可验 |
| **C 派** | **少量短常驻**（世界类型、制度不变量、互斥开局），其余按需；反对"全员履历塞进多个常驻条目" | 群像多 NPC、触发成本敏感、要控命中字符量 |

口诀：蓝灯 = 必须始终存在的信息；绿灯 = 按需加载的信息。蓝灯过多 → token 爆炸；绿灯过多 → AI 缺信息开始猜测。

绿灯配套 `scan_depth=2`（只看最后一条 user + 最后一条 assistant）。**不设 `scan_depth`（默认 null=扫全量）是高频错误**——角色被提一次后 20 轮不出场，AI 仍每轮从历史扫到关键词，条目持续激活、剧情推不动。`sticky`/`cooldown`/`delay`/`probability` 默认 0/0/0/100，无明确设计理由不动。`disable=true` 用于"控制器按需加载"或"作者手动开启"；B 派要求 root + `extensions` 双层设，`content` 首行写 `<!--【手动条目】…-->`。

## 7. 世界书 vs 角色 `description` 的职责边界

| 派 | 做法 | 依据 |
|---|---|---|
| **A 派** | **`description` 字段不写任何内容**；角色全部信息（基本档案、外貌、背景、关系、性格）放进世界书条目，性格再独立成条 | worldbook-skill 铁律 2 + 分支三 Step 5 |
| **B 派** | `description` 写：身份 + 外貌（未载则声明）+ 性格层次（表层/深层/破绽前兆）+ 关系一句定性 + 能力概览（**不泄底粒度**）+ **负空间**；`personality` 放语言指纹与活跃层例句 | ln-lore-pipeline 阶段 6 |
| **C 派** | **优先复用稳定平台字段**；人物核心条目"单独加载也不会失去人格"；母稿详档未导出或无触发路径＝模型游玩时不知道 | chunshui §5 |

> **默认立场（实测修正 · [Personal experiment] 2026-11-07）**：单角色卡默认走 A 派「`description` 留空、信息全进世界书」。
> 实测 5 张成熟卡里，字数最大的两张（64 条 / 91 条世界书）`description` **完全为空**，一张 112 字（只写卖点钩子），两张写长（1261 字 JSON 契约、664 字清单）。
> 也就是说：**留空是主流，写满是特例**，而且写满的两种卡型（游戏系统卡、日常互动卡）都有明确理由——见 `15-card-archetypes`。
> 下面四条适用条件用于**判断能不能留空**，不再是「留空需要许可证」。

"`description` 留空、信息全进世界书"的**适用条件**：

| 条件 | 说明 | 不满足时 |
|---|---|---|
| C1 角色条目**全部蓝灯常驻** | 信息每轮都在，缺位不致丢失；单卡天然满足 | 多卡详情为绿灯 → 角色未被提及即无人设 → **必须**留蓝灯角色速览兜底，或改写 `description` |
| C2 世界书随卡分发且已过触发审计 | 否则"保存在硬盘 ≠ 已供模型使用" | 卡要独立分发/无世界书 → 走 B/C 派，`description` 自足 |
| C3 经脚本写入（config.json） | A 派要求 `card-generator.py`/`world-book-create.py`，不手改 | 手改易破字段 |
| C4 卡型已正确判定 | 判错则蓝绿灯全错，留空策略立即失效 | 重判卡型 |

平台对空 `description` 的运行时行为源文件未说明 `[待核]`：上线前实测一次。

## 8. 泄底门控：哪些信息延迟触发

| 手段 | 做法 | 派 |
|---|---|---|
| `disable` 手动条目 | 终局/红线整条 `disable=true`，首行 `<!--【手动条目】剧情推进至第X章后手动启用-->`；`keys` 收窄为**结构性特异性词** | B |
| 指针句 | 活跃条目只留：「后期线详见专属世界书手动条目（剧情推进后启用）。」 | B |
| 触发逻辑尾注 | 每条末行 `<!-- 触发逻辑：…；剧透等级：X -->`，泄底等级可机械统计 | B |
| 触发≠发生 | 关键词命中**只加载资料，不代表事件发生**；条件事件另写前提、一次性/冷却、当前进展，"不因重复提词反复播开场" | C |
| 入口留白 | 入口只提示可观察的身份与动作，"不直接讲出四年前的失误或信件内容"；"需要调查的真相不能在入口旁白全揭晓" | C |
| 角色认知限权 | 角色只知**公共知识**（自身世界正常渠道可得）+ **私有知识**（亲历亲见亲闻）；绝不知自己是虚构角色、故事走向、玩家存在、AI 行为逻辑 | A |
| PI 不遮羞 | `post_history_instructions` 的隐瞒指令**不计泄底**，但"活跃字段已泄的内容不受 PI 保护" | B |

### 9.1 串线

### 9.2 事实一致性

| # | 检查 | 判据 |

## 11. 写作判据（内容层）

| 判据 | 正确 | 错误 |
|---|---|---|
| 白描 | 写做了什么不写"为什么做"；写说了什么不写"用什么语气说"；写场景里有什么不写"像什么" | `嘴角微微上扬，眼中闪过一丝笑意` → `她笑了` |
| 零度写作（总纲） | `【地理】雨隐村——终年降雨，建筑以金属管道和塔楼连接，人口约3000。` | `铁灰色塔楼刺破灰暗天际线，整座城市在水幕中静默呼吸` |
| 信息不重复 | A 类只写虚构层；B 类只写 1~3 个核心差异；C 类分层（总纲→速览→详情） | 复述 AI 已知（东京是首都、修仙要吸收灵气、精灵尖耳） |
| 原创概念带锚点 | 名称→是什么→谁在用→为什么重要（`晶脉`：地下结晶矿脉/驱动所有魔法装置/帝国矿业公会垄断/枯竭已废 3 城） | 只抛名词`存在"晶脉"资源` |
| 删维度测试 | 删掉这设定，角色行为会变吗？不会 → 背景填充，不展开 | 设计 12 种税目 |
| 关系具体画面 | `她给他做便当，连续做了三年` | `感情深厚` |
| 语料纯净 / 矫正不过度 | 语料条目只保留纯对白；`笑了`/`皱眉`/`攥拳`本身就是白描 | 混入动作神态心理；`他的颧骨肌和嘴角肌肉同时收缩` |

**禁词（逐条 Ctrl+F 扫）**：N1 一丝 / N2 一缕 / N3 一抹 / N4~N6 不易察觉·不易觉察·难以察觉 / N7~N8 鲜明对比·形成对比 / N9 弧度 / N10 弯起嘴角 / N11 翘起嘴角 / N12 喉结 / N13 纽扣 / N14 指节发白 / N15 `不是……是……` / N16 `没有……而是……`；比喻 M1 石子 / M2 湖面·涟漪 / M3 拉满的弓 / M4 琴弦 / M5 闪电 / M6 晨光 / M7 星辰；描写禁律 D1 作者视角解释 / D2 语气眼神腔调视线比喻 / D3 描写不存在之物 / D4 对白精确数字（`我等了你1273天`→`三年多`）；另扫八股：似乎·几乎·仿佛·如同·宛如·好像、嘴角微微上扬、眼中闪过一丝XX、带着XX的口吻、极度·万分·无比·深深的、性格标签化。
